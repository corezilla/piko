# FullReview：多角度评审 → 建议 → 清单 → 修改 → 复审 → 提交

## 为什么存在

一个问题往往不是只有一个错因。架构错、边界条件错、并发错、语义漂移错，混在一起看，
reviewer 的注意力会被"最显眼的那个"吃掉，其余的漏掉。本 skill 把 review 拆成**若干独立角度**，
每个角度由一个独立 reviewer 单独看、各自出一份报告，然后**汇总成一份修改建议**，
再对这份建议本身做 review，收敛成**可执行的修改清单**，按清单改，改完复审。

关键在于**分工**：不同角度的 reviewer 不看彼此的结论，避免互相污染（"你说没问题，那我也说没问题"）。
汇总者看全部；清单化的人看建议不看报告；执行者看清单不看报告。

## 何时用

- "对 X 做一次全面 review"
- "review 完直接改"
- "深度审查这个 PR / 这个模块 / 这个设计"
- "多角度看看有没有漏"

**不适用**：单点确认（"这个函数返回什么"）、纯实现任务（直接写代码）、已经知道问题在哪只想修。

## 前置

开始前必须确认，缺一项就问，不要猜：

| 必要输入 | 缺了怎么办 |
|---|---|
| **被审对象**：具体是什么（文件、模块、PR、设计文档、一个具体问题） | 问 |
| **评审基线**：对比什么（当前分支 vs `origin/main`？整个模块？） | 问 |
| **范围边界**：只看什么、不看什么 | 问 |

可选（不提供就用默认）：reviewer 角度集合、是否允许修改、提交信息前缀。

**动手前先读项目规则**：项目根的 `CLAUDE.md` / `AGENTS.md`。那里通常有强制的门禁
（类型检查、测试、lint、门禁脚本）和提交规范。本 skill 的流程必须**包含**它们，不是替代它们。

## 阶段 0 · 冻结基线

**目的**：让所有 reviewer 看同一份东西，后面的结论才可比。

1. 记录当前 commit：`git rev-parse HEAD`。
2. 记录工作区状态：`git status --short`。**如果有未提交的改动，先问用户**——是包含进去还是先搁置。
3. 确认基线 diff 范围：`git diff --stat <base>`。
4. 把 commit hash、基线、范围写进每份报告的头部。

> 基线冻结后**不要再改工作区**，直到进入阶段 5。

## 阶段 1 · 多角度评审

### 1.1 选角度

角度不是固定的清单，是**针对被审对象挑的**。通用起点：

| 角度 | 看什么 | 典型命令/依据 |
|---|---|---|
| **正确性** | 逻辑对不对、边界条件、错误路径 | 读代码、读规格 |
| **接口与契约** | 签名、错误码、语义是否与契约一致 | 对照 `interfaces/`、schema |
| **并发与状态** | 竞态、原子性、fence、重入 | 看事务边界与锁 |
| **数据与持久化** | schema 迁移、幂等、写入与读回一致 | 看 store/migration |
| **资源与清理** | 释放、泄漏、超时 | 看 `close()` / `finally` |
| **安全与权限** | 越权、注入、敏感信息 | 看 policy、路径校验 |
| **可观测性** | 有没有日志/指标能发现这个故障 | 看 observability |
| **测试充分性** | 该测的测了没；断言是否真的断言了 | 看测试文件 |
| **文档漂移** | 文档写的和代码做的还一致吗 | 对照 `docs/` |
| **可维护性** | 重复、命名、抽象层次 | 读代码 |

**挑法**：先读一遍被审对象，**挑 4–7 个真正相关的角度**。不要把上表全用上——
不相关的角度会产出"这里没问题"的空报告，稀释信号。

### 1.2 分派 reviewer

**每个角度一个独立 reviewer**（用 `Agent` 工具并行分派，`subagent_type: "general-purpose"`）。

每个 reviewer 的 prompt 必须包含：

```
被审对象：<具体路径 / 模块 / diff 范围>
你的角度：<角度名 + 这个角度具体看什么>
基线：<commit hash>
约束：
  - 只从这个角度看，不要提其他角度的问题（那些有别人在看）
  - 找不到问题就报告"无发现"，不要凑数
  - 每个发现必须给出：位置（file:line）、现象、为什么是问题、建议怎么改
  - 不要修改任何文件
输出：写入 <报告路径>，格式见下
```

**报告路径**：`docs/91_reviews/fullreview/<问题短名>/<角度名>.md`
（若项目有别的评审目录，遵循项目约定；`docs/91_reviews/` 是 piko 的约定。）

### 1.3 每份报告的格式

```markdown
---
angle: <角度名>
target: <被审对象>
baseline: <commit hash>
reviewed_at: <YYYY-MM-DD>
---

# Review · <角度名>

## 结论
<一句话：有问题 / 无问题 / 只有 N 个问题>

## 发现

### F1 · <一句话标题>  [Critical|Major|Minor]
- **位置**：`path/to/file.ts:123`
- **现象**：<代码或文档里实际是怎么写的>
- **为什么是问题**：<它会导致什么后果；引用规格/契约/测试作为依据>
- **建议**：<具体怎么改；不是"建议加强校验"这种空话>

### F2 · ...

## 没看的
<明确列出这个角度**没有**覆盖的部分——防止读者误以为已经全查过>
```

**发现的质量要求**（这是整个 skill 的成败点）：

- 每条发现要有**位置**、**现象**、**后果**、**建议**四要素，缺一不可。
- 「为什么是问题」必须能引用**依据**：规格条款、契约 schema、现有测试、调用方代码。
  拿不出依据的，降级为 `Minor` 或标为「存疑，需确认」。
- **不要凑数**。一个角度 0 条发现是合法结果，写清楚"看过了什么、为什么没问题"比编三条有价值。
- **不要越界**。看到别的角度的问题（并发/安全），记一句"疑似属于并发角度"交给汇总者，不要自己展开。

## 阶段 2 · 汇总成修改建议

**汇总者看全部报告**，不看代码（避免被自己的第一判断锚定）。

产出一份 `summary.md`：

```markdown
# FullReview 汇总 · <问题短名>

- **基线**：<commit hash>
- **角度**：<angle1, angle2, ...>
- **输入**：<各报告路径>

## 1. 去重与合并
<同一个根因被多个角度报出来的，合并成一条，列出报告它的角度>

## 2. 分级
| ID | 问题 | 来自 | 级别 | 依据 |
|---|---|---|---|---|
| R1 | ... | correctness, interface | Critical | ... |

## 3. 修改建议
<针对每条 R，给出**怎么改**：改哪个文件、怎么改、改完怎么验证>
```

**汇总时要做判断，不是拼接**：

- **去重**：同一根因的多条发现合并，避免改两遍。
- **分级**：`Critical`＝会导致错误结果/数据损坏/安全问题/与契约不符；`Major`＝边界处理缺失、
  可维护性差、有明确退化风险；`Minor`＝风格、命名、文档措辞。
- **排序**：按"根因优先"排——先修根因，再修表现。同一个根因引发的多处症状只修一次。
- **提建议**：不只是合并发现，要给出**怎么改**。发现说"这里没校验"，建议要说"在 X 处加 Y 校验，
  测试放在 Z"。

## 阶段 3 · review 修改建议

**这一步的 reviewer 不看阶段 1 的报告**，只看 `summary.md`——避免被原始发现带跑。

检查四件事：

| 检查 | 问题 |
|---|---|
| **完整性** | 有没有哪个角度的发现被漏掉/被草率合并？ |
| **准确性** | 建议的改法本身对不对？会不会改出新的问题？ |
| **必要性** | 每条修改真的需要吗？有没有过度设计、有没有为了改而改？ |
| **可执行性** | 按清单做的时候会不会卡住？缺什么前置条件？ |

产出 `plan.md`：

```markdown
# 修改清单 · <问题短名>

## 前置条件
<需要先准备什么：依赖、配置、测试数据>

## 清单
| # | 文件 | 改什么 | 关联 R | 验证方式 | 级别 |
|---|---|---|---|---|---|
| 1 | `src/a.ts` | ... | R1 | `npx vitest run tests/a.test.ts` | Critical |
| 2 | `src/b.ts` | ... | R2 | `npm run check` | Minor |

## 明确不做
<被 review 建议里否决的条目，及否决理由——写下来免得以后又提出来>

## 验收
<改完之后怎样算完成：跑哪些命令、看哪些输出>
```

**清单的质量要求**：

- 每一行**独立可执行**：一行一个文件的一次改动，不写"顺便把相关的也改了"。
- 每行有**验证方式**——能跑的命令或能看的输出。
- **级别决定顺序**：Critical 先做，Minor 最后；同一文件的多处改动尽量合并成一行。
- 写「明确不做」——被否决的建议要留痕。

## 阶段 4 · 执行修改

**按清单逐条改，不要顺手改清单外的东西。** 清单是这次改动的**边界**。

发现清单漏了的问题：

1. 如果是**必须改**才能让清单里的改动成立（比如漏了一个导出），直接改，并在最终报告里记一条。
2. 如果是**新发现的问题**，记进最终报告的"清单外发现"，**当场不要改**——除非它会破坏本次改动，
   那就改并记下来。

每改完一条，跑该条的验证方式。改不动或验证不过的，**不要跳过**，记进最终报告的"未完成项"。

**不要 commit。** 提交是阶段 6 的事。

## 阶段 5 · 复审修改

**重新 review 改完之后的东西**——不是重跑阶段 1，而是看**改动本身有没有引入新问题**：

| 看什么 | 问题 |
|---|---|
| **正确性** | 改后的逻辑对吗？边界还覆盖吗？ |
| **回归** | 有没有破坏别的东西？（跑项目全套门禁，不只是清单里的单条） |
| **完整性** | 清单里的每一条都改了吗？有没有改了一半？ |
| **风格一致** | 新代码和周围的写法一致吗？ |
| **测试** | 这次改动有没有对应的测试？测试是不是真的断言了新行为？ |

产出 `post-review.md`：

```markdown
# 复审 · <问题短名>

## 结论
<通过 / 有问题（列出）/ 未完成>

## 清单执行情况
| # | 状态 | 备注 |
|---|---|---|
| 1 | 完成 | ... |
| 2 | 未完成 | 原因：... |

## 新引入的问题
### PR1 · <标题> [Critical|Major|Minor]
- **位置**：
- **现象**：
- **为什么是问题**：
- **建议**：

## 门禁结果
<跑了哪些命令、结果如何>
```

**复审发现问题就修**（这是流程的一部分，不是可选的）：

- 修完再复审一遍改动，直到复审通过或剩下的都是已登记的未完成项。
- 复审发现的问题如果超出清单范围且影响面大，**问用户**再决定要不要继续改。

## 阶段 6 · 提交与 push

**前置检查**（不全绿不提交）：

1. 项目规定的门禁全部跑过并通过。本 skill **不替代**它们——`CLAUDE.md` / `AGENTS.md` 里写的
   类型检查、测试、lint、门禁脚本，一个都不能少。
2. `git status` 确认没有意外文件（临时文件、探针、编辑器产物）。
3. 确认 `.gitignore` 覆盖了本地产物（证据目录、临时配置、构建输出）。

**提交**：

- **一次提交**装这次 review 的全部改动。清单是连续的，拆成几个 commit 会让"这次改了什么"失真。
- commit message 说明**改了什么**和**为什么**（引用 `R1`/`R2` 这样的问题 ID），不要只写 "fix issues"。
- 结尾按项目要求加 Co-Authored-By 行（看仓库既有 commit 的写法）。

**push**：

- 推之前确认分支和远端：用户没说要 push 就**问**；说了就推。
- 推送后报告 commit hash。

## 最终报告

给用户一份简短总结：

```
角度：<列出>
发现：<n 条，去重后 m 条>
建议：<m 条 → 清单 k 条>
执行：<k 条完成 / j 条未完成及原因>
复审：<通过 / 发现 n 个新问题，已修 m 个>
门禁：<命令与结果>
提交：<hash>，已 push
清单外发现：<有就列，没有写"无">
```

## 常见坑

| 坑 | 后果 | 怎么避 |
|---|---|---|
| reviewer 之间串味 | 一个 reviewer 的结论影响另一个，全是同一个问题 | 分派时明确"只看这个角度"，且各报告互不可见 |
| 角度选太多 | 大量"没问题"的空报告，汇总时信号被淹没 | 只挑 4–7 个**真正相关**的 |
| 发现凑数 | 清单里全是低价值改动，淹没真问题 | 明确允许 0 发现，并要求写"没看的" |
| 汇总只是拼接 | 修改建议之间冲突，改完打架 | 汇总者要做去重、分级、根因排序 |
| 清单太粗 | "把相关的都改了"——没法验证，agent 会顺手扩大改动 | 一行一个文件一次改动，带验证方式 |
| 执行时顺手改 | 改了清单外的东西，复审时说不清 | 清单外发现只记录不改，除非影响本次改动 |
| 跳过门禁 | 提交了坏代码 | 阶段 6 的门禁是硬前置 |
| 基线中途变了 | 各 reviewer 看的不是同一份 | 阶段 0 冻结，阶段 1 结束前不动工作区 |

## 与其他 skill 的关系

- `gitnexus-impact-analysis` —— 改符号前的影响面分析，可以在阶段 4 用
- `gitnexus-exploring` —— 找代码位置，reviewer 需要定位时用
- 项目的 `CLAUDE.md` / `AGENTS.md` —— **门禁和规范在这里**，本 skill 只是加上多角度评审这一层
