# V0.1 RFC: Network hosts enforcement in tool profile (H2 fix)

Status: **Draft, awaiting Project Owner approval before coding**
Author: Claude (sandbox validation, 2026-10-19)
Date: 2026-10-19

---

## 1. Problem

`config/tool-profiles.json` declares `permissions.network_hosts` for
each external tool (currently `mem0_lookup` / `mem0_record` /
`graphrag_search`). The pattern `^[A-Za-z0-9.-]+(?::[0-9]{1,5})?$` is
declared and validated by the schema. **The Piko runtime, however,
never reads the field.** No code path extracts, evaluates, or rejects
based on it. The current `graphrag.example.com` placeholder is
documentation, not policy.

This is documented at `docs/91_reviews/v0.1-coding-notes-2026-10-18.md`
§0.6.4 (Issue H2). This RFC proposes the V0.1 fix.

## 2. Why now

- Operators currently believe the host they configure in
  `permissions.network_hosts` is enforced; it is not.
- This means a malformed Piko config (e.g. mem0_lookup allowed but
  pointing at an unrelated proxy) is silently accepted.
- The discrepancy between declared and enforced policy is a
  footgun, and tooling that *reads* the policy (dashboards, audits)
  would mislead operators.
- Adding enforcement is small in code surface; the design choice
  to make is where enforcement lives.

## 3. Design choice

Enforce at **`applyToolRecoveryPolicy`** — the single policy middleware
point that already wraps every external tool today
(`src/pi-runtime.ts:129`). It is the natural choke point: every
external-tool invocation passes through it; the policy object is
in scope there.

### 3.1 Active-policy handoff

Tool implementations call `globalThis.fetch(url, init)` internally
(`src/mem0-client.ts`, `src/graphrag-client.ts`). Enforcement cannot
see URL from outside `execute()` because the URL is constructed
inside the closure. Therefore, policy must be *active* during
the tool's execute scope, not queried post-hoc.

We adopt a **module-scoped "active allowlist" variable** in a new
file `src/tool-host-policy.ts`:

```typescript
// src/tool-host-policy.ts
let activeAllowlist: readonly string[] | null = null;
export function enterNetworkScope(allowlist: readonly string[]): void {
  activeAllowlist = allowlist;
}
export function exitNetworkScope(): void {
  activeAllowlist = null;
}
export function currentAllowlist(): readonly string[] | null {
  return activeAllowlist;
}
```

The tool-profile wrapper sets the scope on entry, clears on exit,
around the delegated `execute()` call.

### 3.2 fetch wrapper

Piko-internal `fetch` is replaced **per process**, registered at
PiRuntime construction or per `applyToolRecoveryPolicy` call site
(currently `src/pi-runtime.ts`). Choice: register once in PiRuntime
constructor (per-instance), since this is single-tenant.

The wrapper:

```typescript
async function policyFetch(input: RequestInfo | URL, init?: RequestInit): Promise<Response> {
  const allowlist = currentAllowlist();
  if (allowlist && allowlist.length > 0) {
    const url = typeof input === "string" ? input : input.toString();
    let parsed: URL;
    try {
      parsed = new URL(url);
    } catch {
      throw new PolicyViolationError("invalid_request", `not a URL: ${url}`);
    }
    const host = parsed.host.split(":")[0];  // strip port
    if (!allowlist.includes(host)) {
      throw new PolicyViolationError(
        "host_not_allowed",
        `host ${host} not in policy allowlist`,
      );
    }
  }
  return globalThis.fetch(input, init);
}
globalThis.fetch = policyFetch;
```

The host comparison strips `:<port>` (Mem0 GraphRAG-style) so
`api.mem0.ai` matches `https://api.mem0.ai:443`. It **does not**
match `api.mem0.ai.evil.com` (no suffix matching).

### 3.3 Error class

`PolicyViolationError extends Error { name, code, message, host? }`:

```typescript
export class PolicyViolationError extends Error {
  constructor(
    readonly code: string,
    message: string,
    readonly host?: string,
  ) {
    super(message);
    this.name = "PolicyViolationError";
  }
}
```

The tool's existing `try { await … } catch (e)` block catches it and
returns a fallback content (`content` text / `details` carry the
code, host). This way the agent gets a clean error message rather
than a thrown-and-broken task.

The fallback content shape (parallel to `memory unavailable:` /
`doc search unavailable:`):
```
policy violation: host_not_allowed (api.example.com)
```

### 3.4 Backward compatibility

| `permissions.network_hosts` | Effect |
|---|---|
| `[]` (empty array) | **No enforcement.** Tool runs as today. |
| `undefined` | Schema-required when `external` effect; empty array means no enforcement; not specifying is impossible in valid config |
| `["api.mem0.ai"]` | Only `api.mem0.ai` requests are allowed; requests to other hosts throw `PolicyViolationError` |
| Multiple entries `["a.com","b.com"]` | Either match allowed |

We **do not** auto-derive host from `identity.memory.base_url` /
`identity.doc_search.base_url`. Operator manages `network_hosts`
explicitly. This keeps the model simple (single source of truth for
the per-tool allowlist) and avoids silent coupling between
`identity.*.base_url` and tool profile.

## 4. Edge cases

- **No URL (relative path)** — tools that don't issue HTTP:
  `activeAllowlist` is set in scope but no `fetch` is invoked;
  no enforcement happens. Empty allowlist + no fetch is a no-op.
- **URL parsing failure** — `new URL("not a url")` throws
  `TypeError`; we re-throw as `PolicyViolationError("invalid_request")`
  with the bad input in the message.
- **IPv6 literals** — `new URL("http://[::1]:8000/x").host` returns
  `"[::1]:8000"`. The host strip `.split(":")[0]` would yield
  `"[::1]"` (correct). For V0.1, allowlist matches the bracketed form
  literally; V0.2 can normalize. **Documented limitation.**
- **Port-only differences** — `api.mem0.ai:443` vs `api.mem0.ai`:
  the host part is normalized, so both match an allowlist entry
  `api.mem0.ai`. ✓
- **Wildcards / regex** — schema already disallows; we don't
  reintroduce. Operators write exact hostnames.
- **fetch from non-piko code** — the wrapper is `globalThis.fetch`,
  so Node's stdlib (e.g. `node:test` runner internals, `npm ls`-style
  introspection) might be matched. Mitigation: tool execution paths
  in `src/{mem0-client,graphrag-client}.ts` only; external stdlib
  HTTP is rare and getting blocked is acceptable for V0.1 since we
  only run piko-node and tests inside the scope.
- **Concurrent tools** — V0.1 PiRuntime is **single-threaded for
  tool calls** (one tool executes at a time per task). Module-scoped
  state is safe.

## 5. Test plan

New tests in `src/tool-host-policy.test.ts`:

1. `currentAllowlist()` returns null by default
2. `enterNetworkScope(["a.com"]) / exitNetworkScope()` round-trips
3. Policy wrapper blocks fetch to host not in allowlist:
   ```ts
   enterNetworkScope(["allowed.com"]);
   await assert.rejects(() => policyFetch("https://blocked.com/x"));
   ```
4. Policy wrapper allows fetch when host matches
5. Policy wrapper allows fetch when allowlist is empty (`[]`)
6. Host comparison is exact, not suffix (`evil.com` does not match `api.mem0.ai.evil.com`)
7. Error is `PolicyViolationError` with `code: "host_not_allowed"`
   and `host` field
8. Invalid URL throws `PolicyViolationError("invalid_request")`

Add to `scripts/v0.1-real-env-verify.sh` (in tool integration smoke
section) a check that `mem0_lookup` against Mem0 Cloud works after
config update: change placeholder host to `api.mem0.ai`, run day-1,
expect 5/5. (Previously these passes would silently fail on host
mismatch, masking Cloud-vs-selfhost routing bugs.)

## 6. Migration

Existing `config/tool-profiles.json` already declares the correct
hosts:
- `mem0_lookup` / `mem0_record`: `["api.mem0.ai"]` (Cloud) — already
  correct
- `graphrag_search`: `["graphrag.example.com"]` (placeholder; V0.1
  still allowlisted as `graphrag.example.com`)

Operationally:
- Operator deploys with `graphrag_search.network_hosts = ["graphrag.example.com"]`
  + `identity.doc_search.base_url = "https://graphrag.example.com"`
  → requests succeed (or fail with HTTP error from the backend).
- Operator switches `identity.doc_search.base_url` to a different
  host and forgets to update `network_hosts`
  → piko blocks at network check (good failure mode!)

We explicitly document in `piko-doc-search.md` that
`network_hosts` and `identity.doc_search.base_url` MUST be kept in
sync (this is the operator's responsibility).

## 9. Risk & blast radius

- **HIGH** for `src/tool-recovery.ts` and `src/pi-runtime.ts`
  per gitnexus. Workaround: keep the changes additive (only enter/
  exit scope; do not alter existing tool behavior), and gate the
  `globalThis.fetch` swap behind a constructor flag
  `enableNetworkPolicy` that defaults to `true` but can be flipped
  off in tests.
- The 8 unit tests are isolated to a new file; existing tests
  must continue to pass with the wrapper active. **The test file
  `tools/*.test.ts` needs an `enterNetworkScope([])` line at the
  top, or PikoPolicy.fallback behavior must wrap tests' mock fetch
  side. Plan: tests that already mock `globalThis.fetch = mockFetch`
  can keep doing so if our `policyFetch` reads from current
  allowlist; if allowlist is empty, fetch proceeds; if mock
  replaces globalThis.fetch, the wrapper is gone. **Decision:
  tests replace `globalThis.fetch` to install their mock; Piko's
  wrapper is bypassed for the test call. We need to make sure
  that Piko's wrapper reads from the *current* `globalThis.fetch`
  chain — so test mocks stay first-class.**
- Final design check: `policyFetch` MUST call `globalThis.fetch`
  (which at runtime is `node:fetch`'s built-in fetch, and at
  test time is the mock function test installed). Test mode
  should work transparently.

## 10. Decisions (locked, do not re-open)

These three open questions are answered here so the design is
**complete** before any code is written.

| # | Decision | Rationale |
|---|---|---|
| 1 | `permissions.network_hosts: []` empty = **no enforcement** | Backward compatible: a tool that hasn't declared an allowlist behaves as today. No silent surprise, no schema break. Operators who want enforcement add it explicitly. |
| 2 | `policyFetch` is installed **per-PiRuntime-instance**; restored to the prior `globalThis.fetch` in `PiRuntime.close()` | Multi-runtime tests need isolation. Per-instance keeps it scoped. `close()` is the natural teardown; we already have it for `onRawUsage` env cleanup. |
| 3 | **No `PIKO_POLICY_SCOPE=disabled` env opt-out** | Fewer footguns. Tests that need bypass can call `enterNetworkScope([])` directly. Operator-of-last-resort bypass requires commenting out the wrapper install in `pi-runtime.ts` — not blessed, but discoverable. |

Edge case for #1 that needs explicit code:
when `network_hosts: []` is empty AND no `enterNetworkScope()` call
is made, `currentAllowlist()` returns `null` (initial state) and
the wrapper short-circuits. Also handled explicitly inside the
wrapper: `if (allowlist && allowlist.length > 0)` — both null and
empty list yield "no enforcement".
