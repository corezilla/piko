## 1. 编码时严格遵循 ISD 的发现

### 1.1 ISD 含糊 / 不一致

**Issue A1**：`base_url` 文档未明确 Cloud 默认值

- 位置：identity-contract §3.1
- 现状：`base_url` optional，`format: "uri"`
- 我的实现：`baseUrl ?? "https://api.mem0.ai"`
- 影响：低，默认值一致

**Issue A2**：`user_id_template` 字段文档有歧义

- 位置：identity-contract §3.1、system-design §7
- 现状：写了 "default: ${role}:${project_name}" 但 V0.1 没真用模板
- 我的实现：**未实现模板**，直接用 `${role}:${project}` 字面拼接
- 影响：低，V0.1 保留接口供将来；如严格要求 ISD §3.1，应该实现 `user_id_template` 替换逻辑

**Issue A3**：`runtime_config_validation_2026-10-18` 字段模式

- 位置：identity-contract §3.1
- `role.pattern: ^[a-z_][a-z0-9_]{0,63}$`（必须小写开头）
- `name.pattern: ^[A-Za-z0-9._:-]{1,128}$`
- 实际：types.ts 没模式约束（TypeScript 类型层面不强制）
- 我的实现：按 schema 写，TypeScript 类型跟 schema 略不一致
- 影响：低；schema 是运行时校验，TypeScript 是编译时；schema 严格

### 1.2 schema 跟 types.ts 不一致

**Issue B1**：`role` / `name` 在 schema 有正则，在 types.ts 是裸 `string`

- 位置：types.ts `RuntimeConfigIdentity`
- 影响：低，运行时 Ajv 校验
- 修改建议：在 types.ts 加类型守卫或注释说明

### 1.3 我做的设计外添加（需确认）

**Issue C1**：tsconfig.json path mapping 改

- 原：`"typebox": ["upstream/pi/node_modules/typebox"]`（目录）
- 改：`"typebox": ["upstream/pi/node_modules/typebox/build/index.d.mts"]`（具体文件）
- 原因：NodeNext + paths 解析时目录不识别，需要具体文件
- 这是 **STD 之外**的修改（修 tsconfig 不在 ISD 列出的文件里），但需要改才能让 `src/skill-tools.ts` 编译通过
- 修改建议：纳入 design review

**Issue C2**：`src/mem0-client.ts` 错误处理增加了字段填充 fallback

- ISD §11.4 步骤 7 说映射字段，但没明确"字段缺失时怎么办"
- 我的实现：每个字段缺失时给默认值（`r.id ?? ""`）
- 这是合理的失败处理，但**严格来说 ISD 没要求**
- 修改建议：在 ISD §11.5 数据结构字段详情里加"字段缺失时行为"列

**Issue C3**：`src/skill-tools.ts` `validateContext` 抽成独立函数

- ISD §11.1 把校验放在工厂函数流程里说，没说抽成独立函数
- 我的实现：抽出 `validateContext` 复用 lookup 和 record
- 这是 DRY 重构，不改变行为
- 修改建议：ISD 可以记录"`validateContext` 为私有 helper（代码 DRY）"

### 1.4 ISD 实际不可达 / 需修

**Issue D1**：`pi-runtime.ts` 构造函数 `mem0ApiKey?: string` 参数位置

- ISD §8.1 签名：`constructor(config, registry, store, channel, apiKey, mem0ApiKey?)`
- 我的实现：`constructor(private config, ..., apiKey: string, mem0ApiKey?: string)` —— 注意我用了 TypeScript parameter property 简写，把前 4 个标 `private`，mem0ApiKey 单独
- 影响：低，行为一致；但 `private` 修饰符的位置需要审
- 修改建议：ISD §8.1 描述应明确 parameter property 的用法

**Issue D2**：`src/pi-runtime.ts` `available` 变量类型

- ISD §2.f 写：`Record<string, AgentHarnessTool<any, any, any>>`
- 我的实现：实际是 `Record<string, any>`（因为 `applyToolRecoveryPolicy` 的精确签名是 `AgentHarnessTool<ExecutionToolContext>`，跟我加的 skill tools 的更宽泛类型有冲突）
- 影响：低；TypeScript 类型收紧，运行时正确
- 修改建议：ISD §2.f 类型应放宽或具体指定 `Record<string, AgentHarnessTool<any, any, any> | AgentHarnessTool<ExecutionToolContext, TParameters, TDetails>>`

**Issue D3**：`src/pi-runtime.ts` `execute()` 内 `available` 不通过 `Object.entries` 后续过滤

- ISD §2.f 写：
  ```typescript
  const available = Object.entries(profile.tools).map(...).filter(Boolean);
  ```
- 我的实现：先建 `available` map（with skill tools），再 `Object.entries(profile.tools).map(...)` 过滤
- 行为一致，但实现细节跟 ISD 示例不同
- 影响：低
- 修改建议：ISD §2.f 例子应明确"先注册 skill tools 到 available map"

### 1.5 测试相关

**Issue E1**：`result.content[0].text` 类型断言

- Pi 的 `content` 是 `Array<TextContent | ImageContent>`，union 类型没有 `text` 字段
- 我的测试用 `(result.content[0] as { type: "text"; text: string }).text`
- 这暴露了 Pi 的 `AgentToolResult` 设计：`content` 是 union 而非总是 TextContent
- 修改建议：在 ISD §11.2 / §11.4 增加"content 字段类型"说明（mem0_lookup / mem0_record 只产生 text content）

**Issue E2**：mock fetch 替换 `globalThis.fetch`

- node:test 里需要 mock `globalThis.fetch`
- 我的实现：每个测试 set/restore `globalThis.fetch`
- 改进方向：可用 `vi.mock`（vitest）或 `mock.method(fetch)`（node:test 22+）
- 影响：低
- 修改建议：保持现状即可

### 1.6 文档外修改

**Issue F1**：修改了 `tsconfig.json` 的 typebox path

- 详情见 §1.3 Issue C1
- 这是因为 NodeNext module resolution 对目录形式的 paths 不识别
- 真实环境跑 validate-design 时这个改动也要保留
