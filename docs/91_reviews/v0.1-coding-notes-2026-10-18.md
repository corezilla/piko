## 0. V0.1 GraphRAG 集成发现（2026-10-18 追加）

**触发**：用户判定 V0.1 没有 GraphRAG（设计/STD 语料检索）能力 → 不能算 V0.1 实现 → 把 GraphRAG 加回 V0.1。

### 0.1 集成模型决策

- **SIBLING（identity.memory + identity.doc_search），不是 provider-switch**
  - 理由：两者作用域天然不同（per-role 短经验 vs 项目级文档语料）
  - 强制二选一会让全功能运维必须在两个 Piko 进程跑
- **Provider 硬编码 `mem0` / `graphrag`**：V0.1 不引入判别联合，等真要加新 provider 再升级 schema

### 0.2 HTTP API 契约由 Piko 端定义

- 没有公认 GraphRAG Cloud 供应商（2026 现状）
- 我们定义 `POST {base_url}/v1/search` 形状，操作员部署后端必须匹配
- 不假装是"标准"；契约随 operator 反馈迭代到 V0.2

### 0.3 Issues / 待办

**Issue G1**：`config/tool-profiles.json` 的 `graphrag_search.permissions.network_hosts` 用了占位 `"graphrag.example.com"`
- 操作员部署真后端后**必须替换**为真 host，否则 `before_tool` hook 会拦截请求
- Schema 不接受 wildcard；占位是临时方案
- V0.2 应引入 per-tool `base_url` 引用（让 profile 自动从 identity.doc_search.base_url 派生 host）

**Issue G2**：`runtime.example.json` 的 `identity.doc_search.base_url` 也是占位
- 操作员必须替换为真 URL；与 G1 一起处理

**Issue G3**：`index` 工具**不**暴露给 agent runtime
- 知识图谱 / 向量索引需要 LLM 抽取，成本高
- V0.1 indexing 是 operator 离线动作
- V0.2 考虑 operator-side HTTP `POST /v1/index`（不入 agent tool 列表）

**Issue G4**：HTTP 契约字段缺失由 client 默认填充（`id=""`, `content=""`, `score=0`）
- 不抛错，方便后端迭代时不立即 break
- 但反讽：缺失字段被静默吞，可能掩盖后端 bug
- V0.2 收紧：后端响应 schema 用 Ajv 校验，缺核心字段（id / content）时报错

**Issue G5**：`scope` 完全由后端定义，客户端不校验
- typo scope → 后端 404 → 工具 fallback `doc search unavailable: not_found`
- agent 端能处理 fallback 文案，自我纠正
- V0.2 应在前端给 operation 暴露 scope list（让 operator 检视合法值）

**Issue G6**：`graphrag` 旧字段被删，新字段叫 `doc_search`
- 不是 bug，是有意为之
- 旧 `graphrag` 字段语义模糊（"graph 检索" vs "memory 检索"），新 `doc_search` 语义明确
- 旧 V0.3 schema 没发布到生产，无向后兼容负担

### 0.7.3 PiRuntime 真跑发现

**Issue K1（runtime build 失败）**：`listen.port` 必须 ≥ 1，schema `^/` 要求 sqlite/tools.profile_registry_path 用绝对路径。
**修复**：构造 `RuntimeConfig` inline 时用 `listen.port: 8787`、`sqlitePath: /tmp/...`、`tools.profile_registry_path: path.join(cwd(), "...")`。
**Issue K1 影响**：piko 的 minimum-viable config 实际比 schema 严格。schema OK，inline `RuntimeConfig` 必须合规，**这意味着任何 dev / 自动化脚本都得避开相对路径**。

**Issue K2（agent 工具权限）**：测试 `task.permissions.write_paths: []` 让 `write` 工具被 `authorizePath` 直接拒了（"path is outside task permissions"），根本没等到 LLM 在不在。
**修复**：给 task 加 `permissions: { read_paths: ["."], write_paths: ["."], tool_profile_ref: "workspace-exec" }`，`.` 表示 workspace 根。
**Issue K2 影响**：piko 默认配置可以验证 schema 但不能跑 agent——任何 production automation 都要小心 write_paths。  
这不是 bug（默认 fail-closed 是对的设计），是写 harness 时容易踩。

**Issue K3（protocol mismatch = 端到端真测的价值）**：单纯 unit 测试每个 adapter 都通过，但真跑才发现：(a) tool profile `network_hosts` hardcoded `api.mem0.ai` 直接把 mock-mem0 在 127.0.0.1:9999 给拒了——H2 fix 在第一次 debug run 时**真的工作**了，agent 优雅降级到 "memory unavailable — network error"。(b) 把 `127.0.0.1` 加进本地调试用的 tool profile，agent 再跑就通了；(c) 真接口契约 vs 假定接口契约只在端到端跑才暴露。

## 0.8 V0.1.2 GraphRAG 切到 OpenSearch `_search`（2026-10-19）

### 0.8.1 问题

Piko V0.1 的 `GraphRAGAdapter` 用一个**自造**的 `POST {base_url}/v1/search` 形状，body 是 `{ query, scope, filters, max_results }`。这是 Piko 自己定义的 contract，**没有公认 GraphRAG Cloud 供应商原生 speak**。真实部署时 operator 必须写 30-50 行 wrapper 把 vendor API 翻成 piko 的形状。

这违背"用业界主流"的工程原则。

### 0.8.2 决定

切到 **OpenSearch / Elasticsearch `_search` JSON-over-HTTP**——vendor 中性、生态最大：
- ES、OpenSearch、Bonsai、Elastic Cloud、AWS OpenSearch Service、自托管都 speak
- piko 端不定义协议，operator 部署 vendor 实例就能用
- 不需要 wrapper

### 0.8.3 改动

**`src/graphrag-client.ts`**（commit `ce1224a`）：
- URL：`POST {baseUrl}/{index}/_search`（`index` = `options.scope` || ctor 的 `defaultScope` || `"all"`）
- Body：`{ size, query: { multi_match: { query, fields: ["content^2","title"], type: "best_fields" }, bool?: { filter: [{ term: {k: v} }] } }`
- Response：`hits.hits[*]._source`（`{_id, _score, _source: {content, metadata, created_at}}`）
- Auth：`Authorization: Bearer <key>`（OpenSearch 2.x 也接受 `ApiKey`，如 operator 走网关）
- piko `filters: { foo: "bar" }` → OpenSearch `bool.filter: [{ term: { foo: "bar" } }]`
- Error 4xx/5xx → `GraphRAGApiError`（404 仍是 `not_found`——典型如 unknown index）

**ctor 多了 `defaultScope` 参数**（v0.1.1 → v0.1.2 新加）：
```ts
new GraphRAGAdapter(baseUrl, apiKey, defaultScope?: string)
```
`pi-runtime.ts` 把 `config.identity.doc_search.default_scope` 传进去。

### 0.8.4 mock + 验证

**`scripts/mock-graphrag.ts`** 重写成 OpenSearch `_search` 形状，80 行 Node stdlib，包含：
- 路径正则 `/([^/]+)/_search` 抽 index
- `multi_match.query` token-overlap 评分
- `bool.filter` 端到端实现
- OpenSearch 错误壳 `{ error: { type, reason } }`
- `all` / `_all` 当 `_all` 处理返回全语料

**`scripts/mock-mem0.ts`** 也顺带从 v1 迁到 v3（`/v3/memories/add/` 返 `event_id` + status、`/v3/memories/search/` 接 v3 body 形状）——commit `ce1224a` 一并改了。

**E2E**（`LOCAL_STACK=1 ./scripts/v0.1-real-env-verify.sh`）：
- Step 06 Mem0 day-1：5/5 ✓
- Step 07 GraphRAG day-1：5/5 ✓
- 其他 active 步骤全过
- 结果：`All PASS.`

### 0.8.5 docs 同步

- `docs/50_implementation_design/piko-graphrag-impl.isd.md` 同步（v0.1.2 标记、URL/响应 body 改写、风险表改"无 wrapper"）

## 0.9 V0.1.3 skill auto-prefetch at task start（2026-10-20）

### 0.9.1 问题

V0.1 / V0.1.1 / V0.1.2 假设"agent 主动调" skills（`buildSystemPrompt` 写明工具 + 触发条件，让 LLM 自己决定何时查记忆/STD）。这**假设错了**：

- Slinky 派任务过来时，**只给 raw 描述**（"implement the `my-greeter` skill"，不提"查 past experience"或"check STD"）
- qwen3-8b-flash 这类本地小模型**不会**主动调 optional tools——它的失败模式是"忘了查"
- 所以 V0.1 day-1 verify 5/5 通过的**只是 adapter 层**（HTTP 客户端能跟后端通）；agent 实际生产里**不会用**这些 skill tools

V0.1 / V0.1.1 / V0.1.2 verify 漏的就是这个：`piko-debug-run.ts` 跑"写 greeting.ts"任务，agent 用 write 工具但**从不调** `mem0_lookup` / `graphrag_search`——因为任务不需要，agent 也不会自动去查。

### 0.9.2 决定（V0.1.3）

**Skills 改成"每次任务的 prefetched context"，不是 optional tools**：

- `pi-runtime.ts:execute()` 入口（`harness.create` 之前）**自动**跑：
  - `mem0.search(task.instruction, { user_id: \`${role}:${project}\`, max_results: 5 })`
  - `graphrag.search(task.instruction, { scope: defaultScope, max_results: 5 })`
- 结果**注入** `buildSystemPrompt` 的新 `=== Context ===` 段（role 段后、工具说明前）
- agent 一开始就有 relevant past experience 和 design docs 摘要，**不用**主动调
- 三个工具**仍**在 `available` map，agent 任务进行中可补查
- 失败模式：mem0/graphrag 不可达 → 空 context section + log warning，task 继续
- 详细决策（含代码、query 构造、failure mode、test 计划）见 `docs/91_reviews/piko-skill-auto-prefetch-decision.md`

### 0.9.3 改动

- **新文件** `src/skill-prefetch.ts`：`prefetchSkillContext(query, identity, mem0, graphrag, opts?) → {memory, docs, ...}`
  - `Promise.allSettled` + `timeoutMs: 1500`，永不抛
- **`src/pi-runtime.ts:execute()`** 在 `harness.create` 之前 `await prefetchSkillContext(...)`
- **`src/pi-runtime.ts:buildSystemPrompt(task, identity, skillContext?)`** 新加 3rd arg；当传 `skillContext` 时 emit `=== Context ===` 段

### 0.9.6 实现记录（2026-11-03）

代码落地。细节见 `docs/91_reviews/piko-skill-auto-prefetch-decision.md` §9，这里只记要点。

**实现与 RFC 的差异**（都是往更严的方向收）：

- **缓存只在 query 相同时命中**。RFC §7.3 原写「缓存存该 key 最近一次 fetch 的 context，不按 query」——那样会把上一个任务的 context 喂给下一个任务。改成 query 不同就重新 fetch。
- **全失败不缓存**。全部已配置后端都失败时不写缓存，否则一次后端抖动会让整个进程生命周期都返回「backend down」。后端**未配置**（skipped）不算失败。
- **`sources` 区分「没有」和「查不到」**。渲染成不同的话：后者是「prior experience unavailable」而不是「no prior experience found」——不把一次故障说成「语料是空的」。

**实现中发现的三个问题**：

1. **`=== Context ===` 位置错了**。第一版放在工具提示之后，测试断言失败。RFC §2.3 要求在 role 段之后、工具说明**之前**——agent 先读过往经验，再读「你有哪些工具」。已修。
2. **NUL 字节**。缓存 key 的分隔符写成了不可见字符，落盘成真 NUL，文件被当二进制。换成 `|`。
3. **进程级缓存串测试**。e2e 里前一个用例填了缓存，后一个拿到缓存命中，**根本没发 HTTP 请求**——而那用例断言的正是「请求发出去了」。加 `clearPrefetchCache()` 到 `beforeEach`。

**验证**：`tsc --noEmit` 零错误；`npm run test:node` **145/145**（含 24 个 prefetch 用例）；`npx vitest run` **296 pass / 1 skipped / 0 fail**（含 3 个 e2e + 4 个 prompt 断言）；`validate_v03_contract.py` PASS。

**实机（m5air）**：真实 `PiRuntime` + 真实 adapter + mock mem0/mock-graphrag + 真实 oMLX。两个后端都在模型动作之前被访问，然后 agent 跑完写出正确产出：

```
mock-mem0     POST /v3/memories/search/        ← prefetch 先到
mock-graphrag POST /piko-design-docs/_search   ← prefetch 先到
state: completed | elapsed: 1257 ms
```

为此给两个 mock 加了请求日志。踩坑：第一次跑 `elapsed: 17ms` 且无产出——不是 prefetch 把 agent 弄挂了，是 `lane.getResult()` 命中上一轮残留的 Pi durable session，任务被**恢复**而不是重跑（这本身是对的 piko 行为）。清掉残留 session 目录后正常。

**剩下的**：`v0.1-real-env-verify.sh` 的 "prefetch happened" smoke 没做——需要**真实** Mem0/OpenSearch 后端。上面是 mock 后端上的实机证据，真实后端还没验过。这是 V0.1.3 剩下的唯一一项。

### 0.10.7 实机联调发现的三个真 bug（2026-11-03）

代码全绿、部署成功之后，**真连 A7048** 才暴露的问题。这三个都不是「写错了」，而是**单测没覆盖到真实 ssh 语义**：

**1. `-B` 不是 batch mode**（`src/transfer.ts` `sshBaseArgs`）

SSH 凭据骨架里写了 `"-B", "-q"`。在 ssh(1) 里 **`-B` 是 `bind_interface`，要吃一个值**；于是 `-q` 被当成「要绑定的网卡名」吃掉，报 `getifaddrs: -q: no suitable addresses`，然后连接落到不可达路径。**每一次远程执行都返回 exit 255 + 空 stdout**。scp(1) 同样不支持 `-B`。

batch mode 是 `-o BatchMode=yes`（骨架里本来就有）。

**2. `-q` 静音了唯一有用的诊断**

ssh 对**自己的失败**（连不上、认证被拒）和**远程命令真的退出 255**用的是同一个退出码 255，退出码本身分不开。分得开的是 stderr 诊断（`ssh: connect to host … Operation timed out`）——而 `-q` 恰好把这些全静音了。结果：远端主机不可达被报成「命令运行了并返回 255」。

去掉 `-q` 后：不可达 → stderr 有诊断；真实退出 255 → stderr 为空。据此判定 `transport_failed`，事实记 `status=spawn_error` + `exit_code=null`。

**3. 超时不该有退出码**

客户端被杀时，error 上仍带 `code: 255`。直接采信会**伪造一个远程进程从未产生过的退出码**。超时一律 `exit_code=null` + `status=timeout` + `remote_stop_state="unknown"`。

**4. 远程执行没进 `executions[]`，且执行失败不改终态**

`remote_bash` 走 `execRemote` → `execFile("ssh")`，不经过 `DurableNodeExecutionEnv.exec`，所以**一条远程事实都没记**——`executions[]` 是空的，消费者无事实可判。同时 worker 只把 `report_missing` 映射到终态，**没有映射 `execution_failed`**。

合起来的后果正是要防的那件事：**A7048 死了，agent 写下一份格式正确但内容为空的报告，任务照样发布 `Completed`**——消费者看到绿色任务，而它要跑的命令从未运行。

修复：远程执行显式记进同一个 collector；`raw.execution_failed` 与 `report_missing` 同权地改为 `Failed` + `ToolFailure`。

**m5air 实测（A7048 真机）**：

| 场景 | 终态 | `executions[0]` |
|---|---|---|
| A7048 可达 | `Completed` | `status=exited`, `exit_code=0`, output=`a7048-Super-Server\n` |
| A7048 不可达 | `Failed` + `ToolFailure` | `status=spawn_error`, `exit_code=null`, output=`ssh: connect to host <host> port 22: Operation timed out` |

两种情形下 piko 进程都存活、API 正常。

**教训**：`permissions.executables` 那次是「schema 声明了但运行时没消费」，这次是「单测断言了参数存在但没断言参数语义」。**ssh/scp 这类外部二进制的 flag 语义必须用真实二进制验证，不能靠记忆**——`ssh -h` / `scp -h` 的 usage 文本就是权威。

新增回归测试：`tests/unit/remote-exec.test.ts`（白名单 fail-closed、argv 不拼字符串、非零退出是结果不是异常、超时无退出码、ssh 客户端失败 vs 远程命令失败）、`tests/unit/remote-exec-facts.test.ts`（远程事实入库）、`tests/unit/transfer-ssh-args.test.ts`（argv 形态：不得有「吃值的 flag 后面跟另一个 flag」、不得有 `-B`/`-q`）。

`execRemote` 增加了可注入的 spawn seam（默认仍是 `execFile("ssh", …)`），使整条远程路径无需网络即可测。
